# Streaming Product Analytics Dashboards

Аналитический проект по продуктовым дашбордам для видео-стримингового сервиса (Netflix-like).

Фокус — не на «красивых графиках», а на продуктовых вопросах, метриках и интерпретации.

**Датасет:** [Netflix 2025 User Behavior Dataset](https://www.kaggle.com/datasets/sayeeduddin/netflix-2025user-behavior-dataset-210k-records/data) (синтетический, ~210k записей)

---

## Стек

| Компонент | Технология | Роль |
|-----------|------------|------|
| Хранилище | ClickHouse | Аналитическая СУБД, расчёт метрик и витрин |
| BI | Redash | SQL-запросы и дашборды |
| Оркестрация окружения | Docker Compose | Поднятие ClickHouse + Redash одной командой |
| Трансформации | SQL (VIEW + mart-таблицы) | Очистка, метрики, витрины |

Архитектура данных: **ELT**  
`raw tables` → `v_*_clean` (VIEW) → `mart_*` (таблицы под дашборды) → Redash

---

## Продуктовый контекст

Сервис видео-стриминга: пользователи оформляют подписку, ищут контент и смотрят фильмы/сериалы на разных устройствах.

Данные позволяют анализировать:
- активность (просмотры + поиск)
- удержание
- глубину потребления контента
- различия по сегментам (устройство, тип контента, жанр, тариф)

Ограничение: поле `monthly_spend` шумное и не является ценой тарифа, поэтому полноценную монетизацию (ARPU, выручка) не строим.

## Продуктовые вопросы и метрики

### 1. Здоровье продукта (Overview)

**Вопросы:**
- Как меняется количество активных пользователей во времени?
- Как меняется вовлечённость (время просмотра, досматриваемость)?

**Метрики:**
- DAU (активность = просмотр **или** поиск)
- Average Watch Duration
- Completion Rate (progress ≥ 90% и ≥ 80%)
- Количество сессий просмотра
- Динамика по дням / неделям / месяцам

**Срезы во времени:** день, неделя, месяц

---

### 2. Удержание (Retention)

**Вопросы:**
- Насколько хорошо продукт удерживает пользователей?
- Как выглядит retention на день 1 / 7 / 30?

**Метрики:**
- Day 1 / Day 7 / Day 30 Retention (взвешенный: `sum(retained) / sum(cohort_size)`)
- Retention-кривая по `day_n`
- Размер когорт во времени

**Когорта:** дата первой активности (watch или search)

**Наблюдение:** взвешенный retention ≈ 2.5% — низко для реального стриминга, особенность синтетических данных.

---

### 3. Вовлечённость и потребление контента (Engagement)

**Вопросы:**
- Сколько в среднем смотрят и какой процент досмотра?
- Есть ли различия по устройствам, типу контента, жанрам, тарифам?

**Метрики:**
- Average Watch Duration
- Completion Rate (90% / 80%)
- Сессии и вовлечённость в разрезах

**Срезы:**
- устройство (`device_type`)
- тип контента (`content_type`)
- основной жанр (`genre_primary`)
- тип подписки (`subscription_plan`)

**Наблюдение:** вовлечённость почти не отличается по тарифам — в этом датасете тип подписки слабо связан с глубиной потребления.

---

### 4. Монетизация — без отдельного дашборда

**Вопросы, которые хотели закрыть:**
- Как распределены пользователи по тарифам?
- Связана ли глубина потребления с типом подписки?

**Что сделали:**
- Распределение по `subscription_plan` и сравнение вовлечённости по тарифам включили в **Engagement**
- Отдельный Monetization-дашборд не делали: нет надёжных денежных метрик

## Дашборды

| Дашборд | Что показывает |
|---------|----------------|
| **Overview** | DAU, тренды активности, watch time, completion — «пульс» продукта |
| **Engagement** | Вовлечённость в разрезах (устройство, контент, жанр, тариф) |
| **Retention** | Когорты, Day 1/7/30, таблица удержания, размер когорт |

---

## Ключевые продуктовые решения

1. **Активность** = событие в `watch_history` **или** `search_logs`
2. **Completion** считаем по `progress_percentage` (≥90% / ≥80%), а не по полю `action` (оно слабо согласовано с прогрессом)
3. **Когорта retention** = дата первой активности, не `created_at`
4. `primary_device` / в `users` — профиль; для поведения сессии используем `device_type`
5. **`monthly_spend`** не используем как выручку

Подробнее: `docs/01_data_understanding.md`, `docs/02_data_modeling.md`, `docs/03_dashboards.md`

## Выводы и рекомендации

> Датасет синтетический, поэтому выводы иллюстративные: важна логика рассуждений, а не «решения для Netflix».

### Что видно по данным

1. **Активность**  
   DAU удобнее смотреть на горизонтах 7/30 дней и по неделям/месяцам: дневной график за весь период (~2 года) слабо читается.

2. **Удержание**  
   Взвешенный Day 1 / 7 / 30 retention ≈ **2.5%**.  
   Это низко для реального стриминга и, скорее всего, следствие синтетики (мало повторных визитов), а не «поломки» продукта.  
   Размер когорт к концу периода падает — меньше новых первых активностей; это не то же самое, что падение retention.

3. **Вовлечённость**  
   Completion Rate (progress ≥ 90%) и средний watch time почти **не отличаются по тарифам**.  
   Тип подписки в этих данных слабо связан с глубиной потребления.  
   Поле `action` плохо согласовано с `progress_percentage` → досмотр определяем по прогрессу, не по статусу сессии.

4. **Монетизация**  
   Надёжной выручки нет: `monthly_spend` шумный и не является ценой тарифа.  
   Имеет смысл смотреть структуру пользователей по `subscription_plan` и их поведение, но не строить ARPU/выручку.

### Продуктовые гипотезы (что проверяли бы на реальных данных)

- Низкий retention → копать onboarding, время до первого «успешного» просмотра, качество рекомендаций после регистрации.
- Если на реальных данных вовлечённость тоже не зависит от тарифа → вопрос к ценности Premium (контент, лимиты устройств, качество видео), а не только к цене.
- Сильные различия по устройствам / типам контента (если появятся) → приоритет UX и каталога под лидирующие сегменты.

### Что улучшить в аналитике дальше

- Автоматизировать загрузку и сборку marts (dbt / SQL init-скрипты)
- Добавить retention в разрезе тарифа и устройства
- Считать Stickiness (DAU/MAU) и WAU явно в витринах

## Как запустить

> Акцент проекта — на метриках и дашбордах, а не на полностью автоматизированном pipeline.  
> Часть шагов выполняется вручную (загрузка CSV, создание VIEW/marts).

### Требования
- Docker + Docker Compose
- Свободные порты: `8123` (ClickHouse), `5000` или `5001` (Redash)

### Структура (важное)
```text
.
├── docker-compose.yml
├── .env                  # секреты и настройки (не в git)
├── .env.example
├── tables/               # исходные CSV
├── sql/                  # скрипты создания таблиц, VIEW, marts
└── docs/
```

## 1. Переменные окружения
`cp .env.example .env`

При необходимости поправь пароли в `.env`.

## 2. Инфраструктура
```
# Первый запуск Redash — создать служебную БД
docker compose run --rm redash create_db

# Поднять все сервисы
docker compose up -d
```
Проверка:
ClickHouse: http://localhost:8123/ping → Ok. \
Redash: http://localhost:5000 (или порт, который проброшен у тебя)
При первом входе в Redash создай пользователя-администратора.

## 3. Загрузка данных в ClickHouse

```
# Папка для файлов внутри контейнера
docker compose exec clickhouse mkdir -p /var/lib/clickhouse/user_files/data

# Копирование CSV
docker cp tables/. clickhouse:/var/lib/clickhouse/user_files/data/

# Подключение к клиенту
docker compose exec clickhouse clickhouse-client
```

Внутри clickhouse-client:

```
CREATE DATABASE IF NOT EXISTS analytics;
USE analytics;
```

Далее выполнить SQL из папки sql/ по порядку:

1. Создание сырых таблиц + INSERT FROM INFILE (users, movies, watch_history, search_logs)
2. Создание clean-VIEW (v_*_clean)
3. Создание витрин (mart_daily_activity, mart_engagement, mart_retention, mart_monetization)

Либо вставлять содержимое скриптов вручную в clickhouse-client.

Проверка:

```
SELECT count() FROM users;
SELECT count() FROM v_watch_history_clean;
SELECT count() FROM mart_daily_activity;
```

## 4. Подключение ClickHouse в Redash
1. Settings → Data Sources → New Data Source → ClickHouse
2. Параметры:
   * URL / Host: http://clickhouse:8123
   * User / Password / Database — из .env (например analytics)

3. Test Connection → должно быть успешно

## 5. ДашбордыЗапросы строятся к витринам:
* mart_daily_activity → Overview
* mart_engagement → Engagement
* mart_retention → Retention

Примеры запросов и логика виджетев — в `docs/03_dashboards.md`.
Скриншоты: `docs/dashboards/`.

## Полезные команды

```
docker compose ps
docker compose logs -f redash
docker compose exec clickhouse clickhouse-client
docker compose down
```

## Ограничения текущей версии
* Нет единого init-скрипта, который сам создаёт все таблицы и marts при старте
* Загрузка CSV и прогон SQL — ручные шаги
* Redash-дашборды не экспортируются «из коробки» как код; воспроизводятся запросами к mart_*

Это сделано намеренно: проект демонстрирует продуктовое мышление, моделирование метрик и дашборды, а не production data platform.
