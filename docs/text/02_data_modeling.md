## Слой очищенных данных (Views)

Мы создали промежуточный слой представлений (`v_*_clean`) поверх сырых таблиц.

### Принципы
- Сырые таблицы не изменяем (ELT-подход).
- В VIEW убираем дубликаты и добавляем полезные вычисляемые поля.
- Пропуски и сложные аномалии обрабатываем позже — на уровне расчёта метрик и витрин.
- Materialized View не используем: данные статичны, проще пересчитывать обычные таблицы.

### Созданные представления

| VIEW | Строк | Что сделано |
|------|-------|-------------|
| `v_users_clean` | 10 000 | Дедубликация по `user_id`, возрастные группы (`age_group`), флаг `has_subscription_plan` |
| `v_watch_history_clean` | 100 000 | Дедубликация по `session_id`, флаги `is_completed_90` / `is_completed_80`, бакеты `progress_bucket` |
| `v_movies_clean` | 1 000 | Дедубликация по `movie_id` |
| `v_search_logs_clean` | 25 000 | Дедубликация по `search_id` |

### Важные решения в `v_watch_history_clean`
- **Completion Rate** считаем по `progress_percentage`, а не по полю `action` (оно слабо согласовано с прогрессом).
- `is_completed_90` → `progress_percentage >= 90`
- `is_completed_80` → `progress_percentage >= 80`
- Бакеты глубины просмотра: `0-10%`, `10-50%`, `50-80%`, `80-90%`, `90%+`, `unknown`.

### Важные решения в `v_users_clean`
- Возраст переведён в группы: `under_18`, `18-24`, `25-34`, `35-44`, `45-54`, `55-64`, `65+`, `unknown`.
- `monthly_spend` оставлен без изменений (поле шумное, для монетизации опираемся на `subscription_plan`).

## Слой витрин (Marts)

Витрины — готовые таблицы под дашборды.  
Считаются один раз из clean-слоя (`v_*_clean`) и используются в Redash.

### Принципы
- Сырые данные и clean-VIEW не меняем.
- Витрины = обычные таблицы ClickHouse (не Materialized View), потому что датасет статичный и так проще пересчитывать.
- Каждая витрина отвечает на ограниченный набор продуктовых вопросов.

---

### `mart_daily_activity`
**Дашборд:** Overview  

**Гранулярность:** 1 строка = 1 день  

**Метрики:**
- `dau` — уникальные пользователи с просмотром **или** поиском
- `watch_users` / `search_users` — уникальные по каждому типу активности
- `watch_sessions` — число сессий просмотра
- `avg_watch_duration` — среднее время просмотра (NULL игнорируются)
- `completion_rate_90` / `completion_rate_80` — доля сессий с progress ≥ 90% / ≥ 80%

**Зачем:** динамика здоровья продукта во времени.

---

### `mart_engagement`
**Дашборд:** Engagement  

**Гранулярность:** комбинация срезов  
`device_type × content_type × genre_primary × subscription_plan`

**Метрики:**
- `sessions`, `users`
- `avg_watch_duration`
- `completion_rate_90` / `completion_rate_80`

**Важно:**
- Витрина считает метрики **за весь период** (overall), не по дням.
- `users` нельзя суммировать across строк — один пользователь может попасть в несколько комбинаций срезов.
- Нужна для сравнения сегментов, а не для точного user-level подсчёта.

**Зачем:** понять, где выше/ниже вовлечённость.

---

### `mart_retention`
**Дашборд:** Retention  

**Гранулярность:** `cohort_date × day_n`  

**Логика:**
1. Первая активность пользователя (watch **или** search) → `cohort_date`
2. Считаем, был ли он активен на день 0, 1, 7, 14, 30
3. `retention_rate = retained_users / cohort_size`

**Метрики:**
- `cohort_size`
- `retained_users`
- `retention_rate`

**Наблюдение по данным:** Day 1/7/30 retention очень низкий (~1–3%) — особенность синтетического датасета.

**Зачем:** понять, насколько продукт удерживает пользователей.

---

### Итоговая схема слоёв

```text
Raw tables
v_*_clean        (очистка, флаги, дедубликация)
mart_*           (готовые метрики под дашборды)
Redash           (визуализация)
```
