# Dashboards

## Общий подход

Дашборды построены в Redash поверх витрин ClickHouse (`mart_*`).

Цель — отвечать на продуктовые вопросы, а не просто «показать графики».

Итоговые дашборды:
1. **Overview** — здоровье продукта
2. **Engagement** — вовлечённость и потребление контента (включая разрез по тарифам)
3. **Retention** — удержание когорт

Отдельный дашборд Monetization не делали: в датасете нет надёжных денежных метрик (`monthly_spend` шумный и не привязан к тарифу), а сравнение тарифов по вовлечённости включено в Engagement.

---

## 1. Overview (Product Health)

**Вопросы:**
- Как меняется активность пользователей?
- Какой текущий уровень вовлечённости?

**Содержание:**
- Карточка: DAU за последний день данных
- Карточка: средний DAU за последние 7 дней
- Карточка: средний watch time за последние 7 дней
- Карточка: Completion Rate 90% за последние 7 дней
- График DAU по дням за последние 30 дней
- График активности по неделям (весь период)
- График активности по месяцам (весь период)

**Источник:** `mart_daily_activity`

**Почему так:**
- Дневной график за весь период (~2 года) нечитаем → используем 30 дней + недели/месяцы
- KPI дают быстрый срез «здесь и сейчас»
- Completion и watch time показывают не только «заходили», но и «насколько вовлекались»

## 2. Engagement

**Вопросы:**
- Сколько смотрят и какой процент досмотра?
- Есть ли разница по устройствам, типу контента, жанрам, тарифам?

**Содержание:**
- KPI: avg watch duration, completion rate 90% / 80%
- Вовлечённость по устройствам
- Вовлечённость по типу контента (`content_type`)
- Топ жанров по сессиям и completion
- Вовлечённость по тарифам (`subscription_plan`)
- (Опционально) распределение сессий по `progress_bucket`

**Источник:** `mart_engagement`, частично `v_watch_history_clean`

**Важные решения:**
- Completion считаем по `progress_percentage` (≥90% / ≥80%), не по полю `action`
- Витрина overall (за весь период) — для сравнения сегментов, не для динамики во времени
- Тарифы включены сюда, а не в отдельный Monetization-дашборд

**Наблюдение:** вовлечённость по тарифам почти одинаковая — тип подписки слабо связан с глубиной потребления в этом датасете.

## 3. Retention

**Вопросы:**
- Насколько хорошо продукт удерживает пользователей?
- Как выглядит retention по дням 1 / 7 / 30?

**Содержание:**
- KPI: средний Day 1 / Day 7 / Day 30 retention
- Таблица retention по `day_n` (0, 1, 7, 14, 30)
- Таблица когорт (последние N когорт)
- График размера когорт во времени

**Источник:** `mart_retention`

**Логика:**
- Когорта = дата первой активности (watch **или** search)
- Day 0 = 100%


**Наблюдения:**

- Retention (взвешенный): Day 1 / 7 / 30 ≈ 2.5%

Простой average по когортам выше (~5–7%), потому что мелкие когорты с более высоким retention влияют на среднее так же, как крупные.
Для продуктовых выводов используем взвешенный retention: sum(retained_users) / sum(cohort_size).

Значения низкие относительно реального стриминга — особенность синтетического датасета.

- Размер когорт падает к концу периода — меньше новых «первых активностей», не путать с падением retention

## Как воспроизвести

1. Поднять инфраструктуру: `docker compose up -d`
2. Данные и витрины уже в ClickHouse (см. `02_data_modeling.md`)
3. В Redash подключён datasource ClickHouse
4. Запросы дашбордов строятся к `mart_daily_activity`, `mart_engagement`, `mart_retention`
